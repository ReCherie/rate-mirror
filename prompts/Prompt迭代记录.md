## 〇、重要实测发现（先看这条，决定报告怎么写）

**第一次 V1 测试，DeepSeek 在"深度思考"模式下把 12000/12期/月费率0.6% 算对了**：

- DeepSeek 输出：月 IRR ≈ 1.086% → 名义年化 13.03%、有效年化 13.85%
- 本项目引擎输出：13.03% / 13.84%
- **结论：两者一致** → 这份对话截图不要当"AI 算错"的证据，而要当"**外部交叉验证**"的证据（第三方模型独立算出了和我们引擎相同的数，说明引擎可信）。

⚠️ 因此报告里**不要写"LLM 不会算 IRR"**，会被评委当场反驳。
正确的叙事是：**LLM 能偶然算对单道题，但不能作为产品里的计算组件**——理由见下文四个攻击点。

## 一、V1（无效）：四个攻击点实测（每个都截一张图）

> 规则：**答错就截图当幻觉证据；答对也要截图，记为"单题可做对"，四个攻击点里只要有 1-2 个翻车，混合架构的必要性就成立了。**

### 攻击点 1：含服务费 —— **已实测：方法对了，精度不够**
发送：
> 借款 10000 元，分 12 期，每月还 900 元，另收取 800 元一次性服务费。请计算真实年化利率（IRR）。

**实测结果（截图 V1-1-1/2/3）**：它正确地把实际到手写成 9200 元（10000−800），方程也列对了，
解出月利率 r ≈ 2.545% → 简单年化 **30.54%**、复利 **35.2%**。

| | 模型 | 我们的引擎 | 差 |
|---|---|---|---|
| 名义年化（月 IRR×12） | 30.54% | **30.69%** | −0.15 个百分点 |
| 复利年化 | 35.2% | 35.39% | −0.19 个百分点 |

**判读**：这一题它算对了方法，但**把月利率四舍五入到 2.545% 才乘 12，丢掉了精度**；
同时它在同一次回答里混用了"简单年化 30.5%"和"IRR 复利 35.2%"两个口径，读者无法判断该信哪个。
→ 结论：**"算得对"和"算得准、口径唯一"是两件事**，金融场景要求的是后者。

### 攻击点 2：口语化、信息不完整的账单 —— **已实测：只给区间**
发送：
> 我买手机分12期，每个月还799，总共借了8000，这个利息高不高？

**实测结果（截图 V1-2-1/2）**：回答"真实年化大约 35%~36%，远高于正规消费金融贷款 20% 以内"。
我们的引擎：**34.82%**。

**判读**：方向正确、量级正确，但只给区间不给定值；且顺手引入了"正规机构 20%–24%"的外部说法（无出处）。
→ 结论：**能定性、不能定价**——没法作为账单核对依据。

### 攻击点 3：批量与格式稳定性 —— **已实测：5 笔全错**
提问（原文）：
> 帮我算这5笔的真实年化利率，只要结果表格：①12000元分12期每月1072；②5000元分3期每月1704.17；③本金8000元分12期每月799；④10000元分12期每月900，另收800元一次性服务费；⑤200000元分36期每月5901.24。

**实测结果（2026-10-27，DeepSeek 深度思考）：**

| 笔 | 模型输出 | 我们的引擎 | 偏差（百分点） |
|---|---|---|---|
| ① | 7.20% | **13.03%** | −5.83 |
| ② | 7.20% | **13.45%** | −6.25 |
| ③ | 19.56% | **34.82%** | −15.26 |
| ④ | 26.48% | **30.69%** | −4.21 |
| ⑤ | 4.35% | **3.96%** | +0.39 |

- **5 笔全错**，平均绝对偏差 **6.4 个百分点**，最大偏差 **15.3 个百分点**；
- ① 直接写成 0.6%×12＝7.2%（把名义费率当年化，正是我们要揭穿的那个错误）；
- **② 与 ① 完全相同（都是 7.20%）**，而 0.75%×12 应为 9%——这是典型的批处理"复制粘贴式"错误；
- ④ 备注里它自己写"已将 800 元服务费计入首期现金流"，**方法叙述正确但结果仍错**。

> 这张截图是全报告最有价值的单张证据：**同一个模型，单题答对 13.03%，五题批量全错**。
> 结论不是"AI 不会算"，而是"AI 的计算不可靠、不可审计、不可规模化"。

### 攻击点 4：可复现性 —— **已实测：同题答案在 30.5%–40.2% 之间漂移**
把攻击点 1 的问题在新对话里重复提问，实测 4 次结果（截图 V1-4-1 ~ V1-4-4）：

| 次数 | 模型给出的年化 | 口径 |
|---|---|---|
| 第 1 次 | 30.54% / 35.2% | 先给简单年化，再说 IRR 复利 |
| 第 2 次 | 30.5% / 35.2% | 同上 |
| 第 3 次 | 34.3% / 40.2% | 月利率算成 2.86%（应 2.545%） |
| 第 4 次 | 34.32% / 40.2% | 同上 |

**同一道题、同样数字，答案从 30.5% 漂到 40.2%，跨度 9.7 个百分点**；正确值 30.69%。
两轮里它把月利率算成 2.86%（实际 2.545%），一步错、年化就多 5 个百分点。

→ 这一条最致命：**金融产品不能同问不同答**，也不能在"简单年化/复利"两个口径间自由切换。

## 二、V2（结构化）：把"算"这一步拿走后

**做法**：`core/parse.py` 用 Function Calling 让 LLM 只输出字段：
```python
from core.parse import parse_bill_text
import json
print(json.dumps(parse_bill_text("借款12000元分12期，月费率0.6%，每月还款1072元"), ensure_ascii=False))
```
**截图要点**：返回的是 JSON 字段（principal / periods / installments / nominal_rate / upfront_fee），没有任何计算。

**实测发现的真实缺陷（已修复，是最好的报告素材）**：
- LLM 把 `installments` 输出成单元素数组 `[1072]`，而不是 12 个元素；
- 后果：现金流只算一笔还款，程序报"现金流无解"；
- 修复：新增 `normalize_installments()` 做长度归一化（单元素复制、不足补齐、超出截断），并加了 4 项单元测试；
- **报告里可以直接写这一段**：LLM 输出不可控 → 必须有工程化兜底 → 这就是"AI 工程化思维"的具体体现。

## 三、V3（最终版）：费用强调 + 少样本 + temperature=0

`core/parse.py` 的 System Prompt 关键约束：
1. 明确列出"服务费、担保费、手续费、保险费"必须识别，绝不遗漏；
2. 声明"你不需要做任何数学计算，利率由下游确定性代码计算"；
3. 信息不足时置 0，不编造；
4. temperature=0 保证可复现；
5. 输出后由 `normalize_installments()` 归一化 + `irr.py` 精算 + 单元测试守门。

## 四、答辩话术（更新版，背这条）

> "单题问答时，DeepSeek 能算对——我们实测过，它给出 13.03%，和我们引擎一致（截图 V1-good）。
> 但**能做对一道题，不等于能放进产品**，我们做了三组实测：
> 一是批量：一次算 5 笔，**5 笔全错**，平均偏差 6.4 个百分点，最大 15.3 个百分点，第 2 笔还和第 1 笔写成同一个数（V1-3）；
> 二是复现：同一道题问四次，答案在 **30.5% 到 40.2%** 之间飘，跨度 9.7 个百分点，正确值 30.69%（V1-4）；
> 三是精度：同一题里它把"简单年化"和"IRR 复利"两个口径混着说，读者不知道该信哪个（V1-1）。
> 所以我们把架构拆成两层：LLM 只做它擅长的『读懂混乱的人类账单』，
> 数学交给 30 行、11 项单元测试、Excel 双重校验的确定性代码。
> 这就是混合架构——它同时解决了准确性、口径唯一性和可审计性。"
